# Duplicate saved-review ID guard — October 25, 2026

Source baseline: build-14 commit `64e8378338b19153677346b45e9f8ef93dd39353`. An isolated Mac harness compiled the production `MealCore` and storage model sources with declared Mac-only file-path and protection adapters. Its 20 synthetic cases completed with zero failures in 0.46 seconds. The duplicate-ID case showed that `delete(id:)` removed **both** reviews sharing an ID, even though the History action promises to remove only the selected review. The unrelated third review remained. The fixture contained no meal or nutrition truth and never entered an app container.

The backend change rejects a decoded file with duplicate review IDs. Existing `load`, `save`, and specific-delete error paths then leave the file unreadable and preserve its bytes. History already presents its storage-read error for this state. Valid and older unique-ID records retain the same decoding path.

Post-change Mac source-derived verification compiled with the same declared adapters and exercised the duplicate-ID fixture: the store reported unreadable, returned no ambiguous rows, rejected save and specific delete, and preserved the original bytes. Current-record and legacy-record decoding, malformed/partial JSON, and invalid-range rejection also passed in that run. Two broader write cases failed in the post-change scratch location: a valid save and the 30-save stress case. A diagnostic adapter observed file replacement/permission errors at that scratch path; these are retained as **unresolved harness-environment failures**, so this run does not establish post-change write-path regression safety. The unchanged build-14 harness separately passed those write cases before this edit. No iOS app, data-protection, locked-device, or concurrent-writer behavior was tested for this change.

Private evidence: the coordinator's isolated storage-source14 probe and the backend scratch probe. Raw synthetic store files and logs remain outside public Git. No user review file was read or changed.

## Independent coordinator follow-up

A separate fixed output-root Mac run used the exact guarded source, the same declared platform/path adapters and the same other 19 case assertions. Only the duplicate-ID expectations, isolated root and source metadata changed. It compiled once (exit 0, 7.064 seconds) and ran once (exit 0, 0.651 seconds): **20 cases, no failures or skips**. The duplicate file was unreadable; load returned no ambiguous rows, save/specific delete were refused and the bytes stayed identical. Valid current/legacy records, a normal save, targeted/final deletion, write failures and 30 serial save/delete cycles passed. The earlier scratch write failures did not reproduce here; their cause remains unresolved and their evidence is retained. Mac protection adapters exclude iOS `.complete` validation.

Independent read-only source review found no material issue in the guard. The availability tradeoff is deliberate: every record in a duplicate-ID file remains withheld until explicit user recovery; there is no automatic deduplication, rewrite or deletion. The existing History error presentation is source-reviewed, not newly exercised for this malformed file in the app.
