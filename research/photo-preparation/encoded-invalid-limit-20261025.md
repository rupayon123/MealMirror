# Encoded-image limit guard — October 25, 2026

The existing data-based `MealPhotoPreparation.downsampledImage` utility passed a prior isolated Mac ImageIO batch with encoded 48 MP JPEG, PNG, and HEIC, EXIF orientations, and malformed/empty prefixes. That batch did not test invalid thumbnail limits. A subsequent small synthetic 320×240 JPEG probe compiled the exact data function with a CGImage-only Mac adapter. Before this edit, `maxPixelSize` values `0` and `-1` both returned a full 320×240 image in this Mac run. Values `1`, `40`, and `10,000` returned 1×1, 40×30, and 320×240 respectively. The probe completed in 0.32 seconds.

The utility now rejects empty data and limits outside 1–2,400 pixels, matching the app's largest intentional label-photo size, and verifies the decoded thumbnail's positive dimensions and longest edge. With the same small fixture after the edit, `0`, `-1`, `2,401`, `10,000`, and empty data returned nil; `1`, `40`, and `2,400` returned bounded results. The post-edit probe completed in 0.34 seconds. Compilation and the probe exited 0.

**Correction to the earlier version of this note:** the statement that no app path calls the data overload is withdrawn. `ContentView.loadSelectedPhotos` loads `PhotosPickerItem` as `Data` and calls `downsampledImageAsync(from: data, maxPixelSize:)` with 1,800 pixels for food or 2,400 for a label. The camera capture path uses the separate `UIImage` overload. Thus the guard protects a production library-photo path against an invalid caller-supplied limit, while current UI callers pass valid limits. The Mac adapter does not verify PhotosUI transfer, UIKit metadata, native iOS behavior, actual camera inputs, or physical-device memory. No recognition, nutrition, or clinical conclusion follows from these synthetic color-quadrant fixtures. No iOS runtime was used in this follow-up; runtime lease handoff was pending.

## Proposed native follow-up after runtime handoff

Use a normal hosted XCTest or small UIKit application test harness containing the exact current data-preparation function, with synthetic encoded files in its own temporary container. The earlier standalone `simctl spawn` probe timed out even on its argument control and predates this guard; do not reuse it as a passing native control. After explicit lease handoff, prove that the host launches and a trivial control assertion completes within 60 seconds. If it does not, stop and retain the first failure rather than treating image cases as attempted. With a working host, run one 320×240 JPEG through limits `-1`, `0`, `1`, `40`, `2,400`, and `2,401`, plus empty and short truncated data. Require nil for invalid inputs and positive, bounded dimensions for valid ones. Next, use small asymmetric JPEG orientations 2, 6 and 8 to inspect transformed pixel corners and UIKit metadata. Bound the test process to 120 seconds and each image case to 15 seconds; record exact source/binary/fixture hashes, exit status, elapsed time, peak resident memory and any unrun cases. Only after a separate heavy-job slot is granted should one encoded 48 MP JPEG be attempted; stop if the host control or any core bound fails. This remains an isolated utility check, not the production photo picker, camera, model or full app journey.

## Independent coordinator check

The separately frozen [Mac adapter check](encoded-limit-verification-20261025.json) compiled the exact baseline and guarded Data function slices together, then ran each once. The baseline exited 6 with two retained rejection failures (0 and −1 returned the complete small fixture); the guarded function exited 0 with 14 assertions passing. The ten common cases retained their expectations; the fixed suite added four extreme/out-of-policy limit cases. Empty/truncated data, valid 1/40/768/1800/2400 limits and the default-size control were covered. The integrated comment was subsequently narrowed without changing executable behavior.

[Apple documents the maximum-pixel-size option](https://developer.apple.com/documentation/imageio/kcgimagesourcethumbnailmaxpixelsize) and the unbounded result when the key is omitted. It does not promise the observed zero/negative behavior. This guard bounds accepted requested limits and verifies output dimensions; it does not bound encoded byte count, decode work or peak memory. Current native/physical, full large-input and recognition gates stay open.
