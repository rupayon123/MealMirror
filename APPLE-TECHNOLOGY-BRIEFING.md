# MealMirror: Apple technology briefing

Reviewed October 24, 2026. This describes the public Challenge candidate and its next technical direction. See [CHALLENGE-READINESS.md](CHALLENGE-READINESS.md) for the exact package evidence and remaining verification gates. This is a technical briefing, not an applicant-written Challenge essay.

## The point to make

MealMirror is an offline, photo-first Swift app playground for people learning to review a meal after a Type 1 diabetes diagnosis. A person can photograph food, review possible clues, correct them, and keep the foods they enjoy. The engineering choice is to separate *what the image might show* from *what a person can confirm*. A photo alone does not establish hidden ingredients, a serving size, carbohydrate grams, or insulin units.

This lines up with Apple's public emphasis on private on-device intelligence, useful fallback when a model is unavailable, and clear control over uncertain AI output. It is an inference about alignment, **not** an Apple endorsement or an award criterion requiring a particular framework. Apple's published Challenge terms judge technical accomplishment, creativity, and applicant-written responses; the public Challenge page also mentions innovation, social impact, and inclusivity. [WWDC25 Foundation Models session](https://developer.apple.com/videos/play/wwdc2025/286/), [WWDC26 Foundation Models session](https://developer.apple.com/videos/play/wwdc2026/241/), [Apple's generative AI design guidance](https://developer.apple.com/design/human-interface-guidelines/generative-ai), [Challenge terms](https://developer.apple.com/swift-student-challenge/policy/), [Challenge overview](https://developer.apple.com/swift-student-challenge/).

## Implemented WWDC26 image path and its remaining evidence

Apple's current Foundation Models documentation describes multimodal image prompting: an app can attach an image to an on-device model prompt, and pair that with Vision-backed OCR or barcode tools. Apple's current iOS 27 guidance demonstrates image inputs and supports attachments such as `CGImage`, `CIImage`, `CVPixelBuffer`, and image file URLs. Apple presents this as general visual reasoning, not a nutrition model, and warns that larger images use more tokens and latency. The capability requires the iOS 27-era SDK and a compatible Apple Intelligence device; model readiness and availability must be checked at runtime. [WWDC26 image-understanding session](https://developer.apple.com/videos/wwdc2026/237/), [multimodal image prompting documentation](https://developer.apple.com/documentation/FoundationModels/analyzing-images-with-multimodal-prompting), [Foundation Models update](https://developer.apple.com/documentation/updates/foundationmodels).

The on-device model is the only Foundation Models route that can preserve an offline meal-review promise. Private Cloud Compute is a separate server-side model option; it must not be used as an invisible fallback in the Challenge playground. If the device, OS, language, or downloaded model does not support or provide the local model, MealMirror must immediately offer its existing Vision/manual route instead of waiting for connectivity or sending a meal photo elsewhere. This distinction follows Apple's documented separation of the on-device model and Private Cloud Compute; it is a product requirement for MealMirror, not an Apple rule. [Foundation Models overview](https://developer.apple.com/documentation/FoundationModels), [WWDC26 Foundation Models session](https://developer.apple.com/videos/play/wwdc2026/241/).

Build 3 calls Foundation Models through [`LocalPhotoAI.swift`](MealMirror.swiftpm/LocalPhotoAI.swift) with the tested ordinary-food classification Guide/instructions now applied. Default guardrails, structured fields, local route and safety gates are unchanged. Refined source and exact-ZIP Simulator builds pass; the exact app renders initial Home only. A separate iOS 27.1 Simulator bundle executed unchanged processing code from the current `6457bc79…` ZIP, commit `c49c209`: the available model returned tentative names for one bundled synthetic image, with zero amount components, no total and no review readiness. The locale and pre-cancelled-entry guards and actual local-store save/read/delete, user-entry provenance and backup exclusion were observed; physical file protection remains unverified. See the [iOS report](research/foundation-models/ios-simulator-20261024.json) and [central evidence](research/foundation-models/README.md), which retains the earlier Mac comparison and errors. This is processing evidence, not a full exact-app UI journey, physical-device, accuracy or network-isolation pass. Build 2 is internal Testing; build 3 is not uploaded, and no public distribution is authorized.

The model request treats all meal photos as different views of one meal, preserves image orientation, and sends no description, label transcription or stored health data into the prompt. A successful empty response remains an unknown result. Only an unavailable model path falls back to Vision. Requests explicitly use the on-device model; they do not select Private Cloud Compute or download model weights. The app keeps its iOS 17 deployment floor, while image-model calls are gated to iOS 27. [Apple release note](https://developer.apple.com/news/releases/?id=10152026a), [Xcode SDK and system requirements](https://developer.apple.com/xcode/system-requirements/).

The historical Mac and external visual-fixture results remain separate from the completed source-derived iOS processing run. None establishes the final app's full interaction journey or physical-device behavior; see [Foundation Models evidence](research/foundation-models/README.md).

Even with that toolchain, model availability must be checked on the target device. Apple's Foundation Models guidance says availability depends on compatible Apple Intelligence hardware and region, the model may still be downloading, and an app should provide a useful fallback. An offline challenge run also needs evidence that the on-device model is ready without a network at judging time. [Foundation Models availability guidance](https://developer.apple.com/documentation/FoundationModels/generating-content-and-performing-tasks-with-foundation-models), [Apple generative AI design guidance](https://developer.apple.com/design/human-interface-guidelines/generative-ai).

The implemented prompt asks for **candidate visible foods and explicit uncertainty**, never a dose or an exact carb count. Output is structured and constrained, with text bounds and a separate reviewable name list. Held-out meal evaluation remains pending; display-text filtering does not validate the meaning or accuracy of a name. A model's fluent answer is not proof that it saw a hidden ingredient or knows grams. Apple specifically advises communicating limitations, allowing correction, testing across diverse people and inputs, and avoiding plausible but harmful hallucinations. [Apple generative AI design guidance](https://developer.apple.com/design/human-interface-guidelines/generative-ai).

If an OS-provided model is unavailable or performs poorly, a small, properly licensed custom on-device model could be evaluated with Core ML/Core AI. That path must fit the Challenge ZIP, work without a download, run on hardware, and pass independent tests on mixed and culturally varied meals plus nonfood images. Apple describes Core ML as on-device inference accelerated by CPU, GPU, and Neural Engine. [Core ML overview](https://developer.apple.com/documentation/coreml). Several candidate models were screened and rejected because coverage or false suggestions were inadequate; see [OFFLINE-MODEL-DECISION.md](OFFLINE-MODEL-DECISION.md).

## Questions an Apple developer may ask

**“Is this Apple Intelligence?”** Build 3 uses Apple's gated on-device model. Its unchanged processing path completed one synthetic-image request in a separate iOS 27.1 Simulator bundle, keeping tentative names outside amounts. [Foundation Models evidence](research/foundation-models/README.md) and the [iOS report](research/foundation-models/ios-simulator-20261024.json) record the scope; physical-device execution and independent accuracy remain unverified. Build 2 in internal TestFlight does not contain this path.

**“Does the meal image or label give a carb or insulin number?”** No. Model names are separate from carbohydrate items and only prefill an editable name; a checked amount is still required. Vision/catalog matches start excluded. Label OCR shows transcription beside the label photo; the person checks its serving size and enters a value manually. Portions, recipes, hidden ingredients, and carbohydrate grams cannot be established from the meal picture alone. The app never computes insulin units.

**“What still needs to be proved?”** The source-derived iOS run verifies limited processing and storage invariants, not broad accuracy or full app readiness. The refined exact ZIP still needs model/clue and fallback interactions through its UI, full journeys, independent meals/nonfood, accessibility and physical offline evidence. The Mac comparison does not establish the cause of earlier guardrail errors. No cloud fallback is selected.

**“Does it really work offline?”** The code and ZIP contain local app resources, and no review screen depends on a server. A physical airplane-mode walkthrough of the final ZIP is still pending. The Challenge is judged offline under the currently published terms. [Challenge terms](https://developer.apple.com/swift-student-challenge/policy/).

**“What is the technical contribution?”** The specific work to show is a photo-first native flow with several meal views, separate local label transcription, an availability-gated on-device image prompt with deadline/cancellation, bounded Vision fallback, explicit unknown results, editable name-only clues separated from carbohydrate values, source-aware carb review, protected local history, and a compact offline playground. The applicant must personally understand, review, and substantially contribute to the final work, and disclose all AI assistance under Apple's rules. [Challenge terms](https://developer.apple.com/swift-student-challenge/policy/).

**“What remains before a strong submission?”** Reliable on-device mixed-meal clues, independently measured abstention, physical-iPhone and offline validation, full accessibility review, an honest three-minute demonstration, applicant-owned essays/disclosure, and a final rules check when Apple publishes the next Challenge terms.
